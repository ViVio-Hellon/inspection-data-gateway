## 全体の特徴

- **列の型はほぼすべて `Text (255)`**（仕掛3ファイルは全列 Text、品質基準は 543/582 列が Text、伝送用ファイルは 98/104 列が Text）。VBA が値をすべて文字列として扱い（`GetString`）、比較のたびに `Val`/`CDbl` で数値化しているのはこのため。
  → SQLite でも **TEXT のまま持つ**（型付きにすると、比較・表示の結果が VBA と変わる）。
- 主キーや ORDER BY 用の列が無い表が多い。VBA は「最初に一致した行」「最後に一致した行」を Access の返却順で決めている。
  → SQLite へ移すときは**元の行順を保存する列（取り込み順）**を足し、読むときは必ずその順に並べる。
- パスワード: VBA は `nlm` を付けて接続している（SQL_追加）。受領ファイルはパスワードなしでも読めたが、ACE で開くと要求される可能性がある（実機確認）。
- 行数（論理行）: 仕掛 SIKALOTNOW 1,961 / SIKAHIKINOW 1,684 / SIKAODRNOW 5,532、PkgSpecData 871。

## 新しく見つかった食い違い（実機確認が必要）

1. **キャスク画面の列名が全角**: UFCask（436–445 行）は SIKALOTNOW の `仕掛` を `rs.Fields("オーダー番号")`・`"ロット番号"`・`"用途コード"`・`"設計_設備コース"`（全角カナ）で読むが、実際の列名は半角（`ｵｰﾀﾞｰ番号` など）。ACE が全角と半角を同一視しなければ、**キャスクのロット読込はエラー処理に落ちている**はず。いまキャスク検査でロットが読めているかを確認したい。
2. **トットのライン名の表記**: UF1 のライン名は半角 `ﾄｯﾄ`・`ﾊﾞﾗﾝｻｰ`。測定機器ID は `ﾊﾞﾗﾝｻｰ`（半角）と `トット`（**全角**）、校正ストレートエッヂ・設備名バーコード・設備仕様は全角 `バランサー`/`トット`。ADO Filter `[ライン]='ﾄｯﾄ'` が全角の行に一致するかで、トットの測定機器チェックが働いているかが決まる。
3. `測定機器ID` に `Test_` と `Test` の2種類のライン値がある。
4. `測定機器ID` の HVC M4・LVC M2 は `用途` が `H191,H207`（用途限定の機器）。DbReturnMicro の「用途条件に一致する最初の行」の対象。
