# 03 移植計画（方針・機能対応表・追加確認事項・工程・検証）

**状態: 判断事項の回答をいただき実装中（2026-10-30）。** 決定は 04 の「決定」節。下の計画から変わった点:

- **データはすべて SQLite**（D4）。アプリは .sqlite3 だけを読み書きし、Access(.accdb) は取り込み（cscript ブリッジで .accdb → .sqlite3）にだけ使う。下の「DB の口を2実装」は SQLite 1実装になる。
- Flask・waitress は `requirements.txt` で入れる（D1、同梱しない）。

## 方針の要点

1. **業務上の結果を VBA と一致させることを最優先**にする。判定・計算・丸め・出力項目は VBA の挙動（不具合を含む）を既定で再現し、直すものは判断事項で1件ずつ決める。
2. **画面は作り直す**。VBA フォームの配置は再現しない。PC（フルHD 前後）の画面で、キーボード入力（測定器の伝送文字列）を止めずに使えることを優先する（3案は「画面レイアウト案」）。
3. **基盤は python-web-tools から複製**し、VBA+Access 移植の部品は db-viewer から持ってくる。業務ロジックは Python だけに置き、JS は表示するだけ（python-web-tools の約束を踏襲）。
4. **データは「DB の口」を1つにまとめて、Access と SQLite を差し替えられるようにする**。今は Access（cscript → VBScript → ADODB → ACE）、後で SQLite に切り替えても業務ロジックは変えない。
5. **使用パスは全部、設定画面で見て直せるようにする**（ご依頼）。VBA でコードに直書きされていたパスも含める。

## どこに作るか

このリポジトリ（`inspection-data-gateway`）に、python-web-tools の基盤を複製した**独立アプリ「UF検査判定」**を作り、業務ツール統合ランチャーから起動する（db-viewer と同じ形。複製元のコミットは `FOUNDATION_ORIGIN.md` に記録）。

## 追加確認事項への設計方針

### Access（.accdb）→ SQLite（.sqlite3）

- **DB 接続方式の変更**: 業務ロジックは `datasource` の関数（VBA の GetRecordsArr / GetFieldsArr / adoSQL と同じ意味）だけを呼ぶ。実装を2つ持つ。
  - `access`: cscript で `bridge.vbs` を起動し、ADODB + ACE で読み書き。結果は UTF-16 の TSV で受け取る（db-viewer の方式。32/64bit の cscript の選び方も同じ）。
  - `sqlite`: 標準 `sqlite3`。Access から変換した `.sqlite3` を読む。
  どちらを使うかは設定画面で DB ごとに選ぶ。**同じ入力で両方の結果が一致することを試験で確認**してから切り替える。
- **SQL方言・データ型の差**: VBA は SQL をほぼ使っていない（`SELECT * FROM 表` ＋ ADO の Filter、直書きは2か所）。絞り込みは Python 側で ADO Filter と同じ規則（`*` のワイルドカード、大文字小文字を区別しない、Null と `''` の扱い）で行うので、方言の差は出ない。列は全部 TEXT で持ち、値は Access が `GetString` で返す文字列と同じ表現にする（数値・日付の書式、Null→""）。
- **行の順序**: ORDER BY が無く「最初/最後の一致」に依存しているため、変換時に取り込み順の列を足し、常にその順で返す。
- **Access 特有の処理**: DAO による物理削除（キャスク梱包板番号）は `DELETE` 文に置き換え（同じ条件）。ADOX はデバッグ用のみで移植しない。`.laccdb` のロック、パスワード `nlm` は Access 実装の中だけで扱う。Compact・Nz・IIf・日付リテラルは使われていない。
- **変換の手段**: db-viewer の取り込み（`bridge.vbs dump` → TSV → sqlite3）を使う。仕掛DBは上流が毎時作り直すので、SQLite 化するなら「上流が sqlite3 も出す」か「こちらで毎時変換する」かを決める（判断事項 D4）。

### 複数PC・同時書き込み

書き込みの量は少ない（ラインPC 7台前後、1検査1行）。それでも次の対策をとる。

| 心配 | 対策 |
|---|---|
| `database is locked` | `busy_timeout` 10秒 ＋ ロック時 1→2→3秒で3回まで再試行（`sqlite_toolkit`）。それでもだめなら**手元に残して後で送る**（下記） |
| 同時更新によるデータ消失 | 共有側は**追記だけ**（検査データ1行、キャスク板番号）。更新する場合は「読んだときの値と違えば書かない」（db-viewer の `seen`） |
| トランザクション | 1検査のヘッダと明細を1トランザクション（`BEGIN IMMEDIATE`）。VBA は DB 登録に失敗してもシートと CSV は書いていたが、Web 版は「手元の記録 → 共有へ送信」の順にし、送れなかったものは送信待ちとして画面に出す |
| 書き込み待ち・リトライ | `outbox_sync.py`（送信IDの一意索引で二重登録を防ぎ、10分後に拾い直す）を検査データの送信に使う |
| 読み取り中に別PCが書く | SQLite は読みと書きを分離する。共有ファイルでは WAL を使わず `journal_mode=DELETE`（WAL は共有フォルダで安全に使えない） |
| 共有フォルダ上の SQLite の妥当性 | SQLite 公式はネットワーク上のファイルの同時書き込みを推奨していない。**作業中のデータは各PCの手元 SQLite**に置き、共有へは短い追記だけを行う。仕掛・マスタは読み取り専用で開く（`mode=ro`）。上流が作り直している最中は VBA と同じく `PLEASE WAIT.txt`・時刻窓で控え側を読む |
| Access のまま共有する間 | ACE は複数PCの同時アクセスに対応しているので、書き込みは今の VBA と同じ1行追記。cscript の起動ごとに接続を開いて閉じる（VBA と同じ） |

### 長時間放置・セッション・日付変更

| 心配 | 対策 |
|---|---|
| DB 接続を保持し続ける | 保持しない。要求ごと（Access は cscript の起動ごと）に開いて閉じる。VBA も呼び出しごとに開閉している |
| 古いデータを持ち続ける | 品質基準の公差表などのキャッシュは**ファイルの更新日時が変わったら読み直す**（VBA は Excel を閉じるまで読み直さない。判断事項 D11）。ロットの情報はロット登録のたびに読む |
| セッション切れ・ブラウザ放置後の再操作 | 検査の状態はサーバ（手元 SQLite）にあり、ブラウザは表示だけ。放置後に操作するとサーバの状態を読み直して描き直す（`health.js`）。打ちかけの入力は `drafts.js`、画面を閉じる前の確認は `unsaved.js` |
| メモリ・ファイルハンドル・ロック | 接続を持たないので残らない。cscript はタイムアウト付きで起動し、終わらなければ止める（db-viewer の `kill_children`）。ログはファイルを開いて追記して閉じる |
| 日付変更・直の切替 | 日付・直は保持せず、**操作のたびに計算**する（夜勤の0時以降は前日扱い、など VBA の規則どおり）。校正の要否も入力のたびに判定（判断事項 D11） |
| マスタ更新後 | 上記のキャッシュの読み直しで反映。検査中のロットの公差は、ロット登録時の値を検査の記録に写して持つ（途中で変わらない） |
| タブを閉じた後 | `idle_exit.py` でプロセスを止める。作業中のデータは手元 SQLite に残り、次の起動で再開できる（VBA の作業中保存と同じ） |

## 検証計画（VBA と同じ入力 → 同じ結果）

1. **関数単位**: VBA の関数ごとに、境界値・例外を含む入力表を作り、Excel 実機で VBA を動かした結果（期待値）と Python の結果を比べる。Excel 側で期待値を書き出すマクロ（`vba_src` の関数をそのまま呼ぶ）を用意する。
   - 対象の例: UnitRecord（.51・1.01 などの Single の境界）、AHTJudg（境界ちょうど）、Diagonal（Single 比較: 1530.4 / 1528.3、公差 2.1）、Height_Check、Format/Round の .5 境界、FindInList（`*`・`≠`・後勝ち）、LoopArray/FindIndices（上端を含む）、TimeDesignation（59:46、00:45、秒が1桁）、直判定（07:00、22:50、0時またぎ）、伝送文字列の解析。
2. **ロット単位（ゴールデン）**: 本番ラインの `保存用`/`耳用` シートと `梱包検査ﾃﾞｰﾀ.accdb` の実データ（測定値と判定の記録）を入力にして、Python で再判定し、記録と一致するか見る。**本番の xlsm と梱包検査ﾃﾞｰﾀ.accdb の写しが必要**（04 の不足資料）。
3. **出力**: 成績票・不良要因票・CSV・Aインプット電文・保存用の1行・梱包検査ﾃﾞｰﾀの1行を、同じロットで VBA と Python の両方から出して項目ごとに比べる。
4. **DB 実装の一致**: 同じ入力で `access` と `sqlite` の結果が一致すること。
5. **運用試験**: 2台以上から同時に登録、長時間放置後の操作、日付・直をまたぐ操作、上流の作り直し中（`PLEASE WAIT.txt`）の読込。
